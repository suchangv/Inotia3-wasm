# Reusing other people's code — what exists, and what to use

Researched 2026-10-16, before writing any renderer. The principle: this port
should be glue, not implementation. Every layer below has a mature
implementation somewhere, and the job is to find it rather than to rebuild it.

## The GL layer: gl4es

**This is the big one, and it changes the plan.**

The original estimate had "GLES1 → WebGL2 fixed function" as a 6-10 week
from-scratch renderer. It does not have to be written.

**gl4es** (`github.com/ptitSeb/gl4es`) is a GLES1 / desktop-GL 1.x → GLES2
compatibility layer. It descends from glshim and is used to run GLES1-era games
on GLES2-only hardware — which is exactly the translation this port needs, one
platform over.

What was verified, not assumed:

* **It exports the complete GLES1 entry-point set.** `src/gl/glesfuncs.inc` is
  a 241-entry `_EX(name);` list. Every fixed-point call this guest uses is in
  it: `glClearColorx`, `glColor4x`, `glOrthox`, `glScalex`, `glTranslatex`,
  `glFrustumx`, `glRotatex`, `glLoadMatrixx`, `glMultMatrixx`, `glTexEnvx`,
  `glTexEnvxv`, `glTexParameterx`, `glLineWidthx`, `glPointSizex`,
  `glDepthRangex`, `glAlphaFuncx`, `glClipPlanex`, `glLightxv`, `glGetFixedv`,
  `glNormal3x`. All present.
* **It has an Emscripten build target**, documented in `COMPILE.md`.
* **It is MIT licensed** — compatible with this repository, no copyleft
  contamination (unlike Unicorn, which is GPLv2 and is therefore only ever used
  here as an out-of-tree test oracle).
* The relevant modules already exist: `fpe.c` / `fpe_shader.c` (fixed-pipeline
  emulation and its shader generator), `matrix.c` (the matrix stack),
  `texenv.c`, `light.c`, `texture_compressed.c`, `framebuffers.c`.

So the chain becomes:

```
guest GLES1  ->  gl4es  ->  GLES2  ->  emscripten  ->  WebGL
                 (MIT, written and debugged by someone else)
```

and `src/gl.c` stops being a state-tracking stub and becomes a thin forwarder.

**Build recipe** (from `COMPILE.md`, with one change):

```
cmake .. -DNOX11=ON -DNOEGL=ON -DSTATICLIB=ON -DDEFAULT_ES=2
```

`DEFAULT_ES=2` is the change: the default backend is GLES 1.1, but under
emscripten the backend *is* WebGL, i.e. GLES2. `NOEGL=ON` means the EGL context
must be created elsewhere — emscripten's own GL context setup does that.

**Verified end to end**, not assumed:

```
$ tools/build_gl4es.sh
== gl4es: <rev> ==
   -> vendor/gl4es/lib/libGL.a (4.7M)

$ emcc linktest.c -o linktest.js vendor/gl4es/lib/libGL.a -sFULL_ES2=1
$ node linktest.js
LIBGL: Initialising gl4es
LIBGL: v1.1.7
LIBGL: Using GLES 2.0 backend      <- DEFAULT_ES=2 doing its job
LIBGL: Targeting OpenGL 2.1
```

It builds, it links into an emscripten program, and it initialises at runtime.

### Two things learned while linking it

* **`-lGL` resolves to emscripten's own GL, not gl4es.** Emscripten ships a
  `libGL` (the GLES2 -> WebGL mapping) in its sysroot, so `-L vendor/gl4es/lib
  -lGL` silently links the wrong library and every gl4es symbol comes up
  undefined. gl4es has to be named by path: `emcc ... vendor/gl4es/lib/libGL.a`.
* **The entry points are `gl4es_gl*`, not `gl*`.** The core implementations are
  prefixed (`gl4es_glOrthox`, `gl4es_glClearColorx`, ...); the unprefixed public
  names are generated by the `_EX()` machinery in `glesfuncs.inc` for the
  shared-library build. There is also `gl4es_GetProcAddress(const char *)` for
  name lookup, and `initialize_gl4es()` / `set_getmainfbsize()` to bring it up --
  the latter required under `NOEGL`, since with no EGL nothing else can tell
  gl4es how big the surface is.

### What the adapter still has to do

`gl4es_GetProcAddress` gives a `void *`, and C cannot call through that without
knowing the signature -- nor can a flat `uint32_t args[]` be cast into one.
The guest's arguments arrive as a word array (registers then guest stack), so
each entry point needs a small typed adapter: unpack the words into the real C
types, and translate guest addresses to host pointers. That translation is the
one thing this port owns here, and it is trivial because the guest address space
*is* a buffer: `guest_addr` -> `g_mem + guest_addr`.

Of the 29 entry points in use, only about eight take a pointer
(`glVertexPointer`, `glColorPointer`, `glTexCoordPointer`, `glGenTextures`,
`glLoadMatrixf`, `glTexImage2D`, `glTexSubImage2D`, `glTexEnvxv`); the rest are
integer or GLfixed arguments. So the adapters are a few hundred lines of
mechanism, not a renderer.

### What was rejected, and why

* **Emscripten's `-sLEGACY_GL_EMULATION`.** Tempting — it is built in and needs
  no dependency. But its own documentation is clear that it emulates *legacy
  desktop OpenGL 1.x* features (immediate mode, `glNormalPointer`), that it "is
  by no means complete", and that it is "less efficient" and not recommended for
  new code. It does not provide the GLES1 API surface — the `x`-suffixed
  fixed-point calls are simply not there. It would cover part of the job and
  leave the part that matters.
* **Writing the renderer.** 3-5 weeks for the ortho path the engine actually
  uses, and it is the highest-risk item in the project. Only worth it if gl4es
  turns out not to build.
* **ANGLE / Regal.** Both are heavier and target different directions (ANGLE
  maps GLES to D3D/Vulkan/Metal; Regal is desktop GL). Neither is a natural fit
  for GLES1 under WebGL.

### Why this is smaller than it looked

Two measurements from the running interpreter narrow it further:

* **Only 29 GL entry points are in use** on the path that runs today, and they
  are all 2D: `glOrthox` for the projection, `glMatrixMode`/`glLoadIdentity`/
  `glScalex`/`glTranslatex` for the transform, client arrays, `glDrawArrays`,
  and texture upload. No `glFrustumx`, no `glLightxv`, no `glNormalPointer`, no
  compressed textures, no framebuffer objects.
* **The engine composites in software.** The texture uploads are 384x256 — a
  framebuffer-sized surface — alongside 512x256 and 512x64 atlases, and the
  profile is full of the engine's own `GRP_FillRect` and `GRP_Filter*` blend
  routines. Much of the 2D drawing happens on the CPU; the GL layer puts the
  result on screen.

So the risky half of "GLES1 fixed function" may not be exercised at all — and
gl4es covers it if it is.

## The browser host: emscripten

Already installed and working: **emsdk 6.0.12** at `~/emsdk`.

The freestanding clang-to-wasm32 build was the right way to get a throughput
number with no dependencies, but it is not the right way to ship: a browser port
needs a filesystem, an event loop, input, audio, and threads, and emscripten
provides all of them. Adopting it replaces several line items at once:

| Need | Emscripten provides |
|---|---|
| Asset loading (926 files, 25.5 MB) | `--preload-file` / `file_packager`, MEMFS, or IDBFS for anything writable |
| Save files | IDBFS — persists to IndexedDB, survives reload |
| Input | SDL2 (`-sUSE_SDL=2`) or emscripten's `html5.h` event API |
| Audio | OpenAL (`-sUSE_OPENAL=1`) or SDL audio, both backed by WebAudio |
| Threads | pthreads with `-pthread`, needing COOP/COEP headers — the same requirement the port would face anyway |
| The render loop | `emscripten_set_main_loop` with `requestAnimationFrame` |
| GL → WebGL | automatic: GLES2 calls map to WebGL 1/2 |

The alternative — hand-writing all of that against the freestanding build — is
where the "2-4 weeks browser host" estimate came from, and it is avoidable.

## What is still worth writing by hand

* **The loader, interpreter, JNI environment, patches and timer table.** These
  are this port's actual content; nothing off-the-shelf does "load this specific
  `.so` into a guest address space and feed it a hand-built JNI environment".
  `lib/so_util` and `lib/falso_jni` in the parent repository are the nearest
  relatives and are already reused for their *logic*.
* **The `WrapperJinterface` Java-side semantics** (fonts, text, sound). The
  parent repository's `source/java.c` and `source/patch.c` encode what these
  have to do; that is a port, not a dependency.
* **The AOT translator.** Covered below.

## The CPU layer: still the place to look

The measured throughput says the interpreter alone gives roughly 3-5 FPS in a
busy scene, so a static translation is on the critical path. Before writing one,
the prior art is worth a serious look — the same principle applies:

* **QEMU's TCG** — a production translator for exactly this ISA family. Its
  *architecture* (translate to an IR, then to a backend) is the proven design,
  and this port's interpreter is already the natural diff target. The wasm
  backend was rejected earlier because framework emulation is the wrong shape
  here, but the translation *approach* is not.
* **RetDec / McSema / remill** — existing ARM → LLVM lifters. Worth evaluating
  for the translation step before writing one, bearing in mind that Thumb-1 with
  a fully static call graph is a much easier input than what they target.
* **Unicorn** — already in use, as the correctness oracle only (GPLv2).

Not researched to the same depth as gl4es; this is the next thing to look at
properly when that work starts.

## Status, and what is blocking

* Researched: gl4es' API surface, licence, build recipe and module layout; the
  emscripten alternative and its limitations; what emscripten provides for the
  host layer.
* Installed and verified: emsdk 6.0.12 (`emcc --version` works).
* **Built and linked and run**: `tools/build_gl4es.sh` produces
  `vendor/gl4es/lib/libGL.a`; a test program links it and initialises under
  node with the GLES2 backend.
* Reproduced by anyone with `tools/build_gl4es.sh`; `vendor/` is gitignored, so
  no third-party tree is committed.
* **Remaining**: the typed adapters between the guest's argument words and
  gl4es' C signatures, and the emscripten host proper (canvas, assets, input).
